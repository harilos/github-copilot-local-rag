# Issue #20: Windows file-I/O audit

Date: 2026-09-04. Task branch: `fix/windows-progress-file-resilience` (task-provided name).

## Scope and interpretation

This is a source-code audit, not evidence that every listed failure has occurred. The reported incident is `atomicprogress` publication failing with `PermissionError: [WinError 5]`. P0 work in this task covers observational progress resilience, bounded atomic replacement retry, and the separately reviewed rebuild scope. Other findings below are follow-up records only: no broad refactor, real database access, credential-file access, network operation, issue/comment creation, or artifact regeneration was performed for this audit.

The table records the baseline implementation inspected during this task; P0 files are being changed in parallel and their final tests/results belong in the task validation report. Paths are relative to `.copilot/rag/`: `G/` means `gen_db/software_rag_tool/software_rag_tool/`, `S/` means `source_manager/`, and `Q/` means `query/`.

Artifact roles: **A** = authoritative content/configuration, **R** = resume/checkpoint authority, **O** = observation/display only, **T** = staging or regenerable temporary artifact. A file can have multiple roles. Atomic replacement protects an individual pathname from partial publication; it does not create a transaction across vector, catalog, clean records, and state. A process-scoped writer lock does not prevent antivirus/indexer/read handles from denying a Windows rename.

Priority: **P0** = reported/current-scope failure; **P1** = separate reliability or recovery work for durable state/content; **P2** = lower-risk staging, display, or consistency follow-up. Recommendations are not authorization to implement additional product cycles.

### Findings from the task's subsequent Windows fixture work

The coordinating implementation agent reported a native Windows concurrent-reader `errno=13` denial during the isolated stress work. The affected status/inventory JSON read paths are `G/status.py::_load_json` and `G/source_inventory.py::_load_json`; their narrowly scoped follow-up uses `G/read_io.py::read_text_with_windows_retry`. This is a reader-side sharing race in the same incident family, not evidence that status or inventory is empty. Exhausted authoritative reads must remain errors, and permanent permissions, malformed JSON, and missing-file semantics must not be collapsed into one retryable/empty result. The final candidate's test report, rather than this source audit, owns the native reproduction and pass evidence.

The same fixture work identified **P1: existing private-scope migration before resume** as a follow-up validation requirement. The new source-scoped rebuild boundary must not be assumed to establish compatibility for every previously created private-scope artifact/checkpoint. A separate fixture should start from a genuine old-layout private scope, exercise the required migration-before-resume ordering, preserve sibling-source records, and compare vector/catalog/clean/state IDs. No real private database was inspected or migrated by this audit, and this report does not claim that compatibility scenario passed.

The task also now includes closed-schema Source result propagation: `observability_degraded` is a boolean and `observability_failed_sinks` is a bounded, unique subset of `progress`/`events`, consistent with the boolean. SharePoint privacy filtering preserves only these fields; ordinary, Redmine/GitLab Issues, and Confluence result paths retain/aggregate them without changing DB success or persisted Source state/event policy. Manager output uses a fixed warning, never a supplied sink path or exception. `source_manager/tests/test_observability_results.py` provides isolated command-result, in-memory Source orchestration, batch/resume, and display contracts; it does not open a real database.
